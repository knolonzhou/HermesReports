### 1. Anthropic 提交 S-1：AI 泡沫论者的弹药库还是真金白银的账本？（1077 分 / 1003 评论）

Anthropic 正式启动 IPO，S-1 里最扎眼的是一串天文数字级算力承诺：Google 1140 亿、AWS 1100 亿、Broadcom 1610 亿、SpaceX 1200 亿美元。另一面是经营数据其实在好转——每 1 美元算力支出换回 2.08 美元收入（2025 年 Q1 还只有 0.40 美元），算力回本周期不到一年。风险章节也罕见直白地承认开源/开放权重模型可能"在某些用例上分走市场"。
👉 为什么值得看：这是头部大模型公司第一次把完整的成本结构、客户集中度和算力对赌摆给公众看，无论你看多还是看空 AI，这份文件都是接下来一年所有争论的数据源头。
💬 评论区吵点：看多派强调 2.08 美元/1 美元的推理经济性和 ARR 增速；看空派则盯着那 5000 亿级别的承诺——"派对继续就是 500 亿营收冲 5000 亿，派对停了就是灭顶之灾"。还有人讽刺风险披露里"开源模型分走部分市场"的措辞，指出当天 OpenRouter 上 token 消耗前五全是中国/开放权重模型。最离谱的高赞：有人真把整份 S-1 喂给 Opus 5.5 让子代理集群"用 200 美元复刻 Anthropic 公司战略"。

### 2. 一位皮肤科医生用 2015 年的 CNN 打脸 GPT-6 和 Claude（646 分 / 265 评论）

伦敦 Guy's 医院的皮肤科顾问医生 Magnus Lynch 拿 200 个全部经活检确诊的皮肤病变（含 30 例黑色素瘤）测试：GPT-6 Astra 和 Claude Fable 5.1 各对 42%，而他用单张 H100 微调约 20 分钟的 Inception v3 对 62%。更吓人的细节：GPT-6 把 30 例黑色素瘤中的 14 例误判为基底细胞癌，两个 LLM 都有"最爱答案"偏置；而 CNN 小到能在手机浏览器里用 WebGPU 跑，数据全部公开可复现。
👉 为什么值得看：这是"通用大模型 vs 专用小模型"之争最干净的一次实测——作者本人是执业医生，测试设计、原始回复、评分代码全部打包开放，没有含糊空间。
💬 评论区吵点：共识派认为这正说明该用 LLM 把专用分类器的构建成本打到近零，而不是拿 LLM 直接当分类器（类比 KataGo：3000 万参数的专用网络下围棋超人类，万亿参数的 LLM 不行）；有人总结启发式——看任务是否在预训练数据中严重过采样且做过 RL 后训练，否则别指望。反对派（自称 MLE）则说拿微调专用模型比通用模型是"不公平比较，不配上首页"，被大量反驳：医生自己都说"我很惊讶"才是真新闻点。

### 7. 上下文工程现状：从"少塞点"进化到"怎么塞"（247 分 / 60 评论）

Drew Breunig 的年度综述把 context engineering 从口号变成工程学科：上下文不是越长越差，关键在信息的组织方式——相关内容离得越近，注意力机制工作得越好（心理语言学的 Dependency Length Minimization 同样适用于 LLM）；记忆系统的下一个难题是"战略性遗忘"，过于精确的记忆会互相冲突，模型会随prompt 里哪个近就信哪个。
👉 为什么值得看：所有写 agent、做 skill、调 harness 的人都能直接抄作业，比如"重要信息放 skill 末尾（离思考块近）+ 关键事实放对话最开头（系统提示权重加成）"这种两头下注的实操技巧。
💬 评论区吵点：实战派分享五花八门的记忆方案——轻量工单系统给 subagent 做上下文交接、Zettelkasten 式 append-only + 定期园艺；抱怨派说 Claude Code 上下文管理远不如 Codex 自动。最高赞的技术讨论是缓存：想删中间某轮无用上下文会导致后续段落缓存全部失效，"压缩上下文"和"省钱"在工程上直接打架。
🔗 [原文](https://www.dbreunig.com/2026-10-24/the-state-of-context-engineering.html) · [HN 讨论](https://news.ycombinator.com/item?id=50235780)

### 9. Ubicloud：把 vLLM 工具调用准确率从 92% 修到 100%（119 分 / 61 评论）

Ubicloud 工程师复盘了一个很多自托管团队都踩过的坑：用 vLLM 服务 Kimi K2.6 时工具调用 schema 准确率只有 92%——每 25 次坏 2 次，agent 多轮会话里错误上下文会滚雪球。解法是打开 vLLM 0.31 新加的 constrained decoding（约束解码），配合 `--tool-strict-level` 标志，K2VV 基准直接 100%。文中解释了 vLLM 为何默认关闭该功能：对某些模型会强行掰 token 导致跑偏，还有语法翻译和投机解码的交互 bug。
👉 为什么值得看：一句话结论对所有自建推理服务的人有用——"你观察到的模型质量不只取决于模型，还取决于推理引擎和它的配置"；换个引擎或开关，同一个模型的 agent 表现天差地别。
💬 评论区吵点：懂行派指出标题党——constrained decoding 早就在 vLLM 里，博主实际只是"配置对了"，文章写得像他们修了 vLLM；还有人想看约束解码对输出质量的真实影响（它改变了 token 分布），对比"失败重试"方案哪个更划算。博主本人在评论区 AMA。
🔗 [原文](https://www.ubicloud.com/blog/fixing-tool-call-accuracy-in-vllm) · [HN 讨论](https://news.ycombinator.com/item?id=50242870)

## 💬 今日吵架冠军：老 CNN 吊打前沿 LLM，到底是打脸还是废话？

**第 2 条**的评论区吵得最凶。反方（不少自称 ML 工程师）说这是田忌赛马：拿专门微调过的分类器比通用模型，就像说计算器乘法吊打 LLM，"不配上首页"；正方回击：这恰恰是重点——KataGo 用 3000 万参数下围棋超人类，万亿参数 LLM 不行，专用架构对专用任务的优势不是新闻而是被大模型热潮淹没的常识，一位执业医生用全公开数据把这件事重新钉死，正该上首页。双方唯一共识：作者把所有 prompt、回复和评分脚本打包公开，比 99% 的"LLM 不行"文章都体面。
